# 面向普通用户的 EvoMap 文章框架草案

图文版飞书文档：<https://ccnjn62goe9e.feishu.cn/docx/So4SdLJOFoz1dvxMP49c6x1gnlh>

## 参考 EvoMap 博客后的判断

参考 EvoMap 中文博客现有文章后，这篇不适合写成“产品介绍”或“协议说明”。站内文章更常见的写法有几类：

- **从 A 到 B**：例如“从文档到进化”“从 MetaClaw 到 Evolver”，先给出变化路径。
- **当 Agent...**：例如“当 Agent 学会主动探索”，把能力说成一个可观察的行为变化。
- **X 不只是 Y**：例如“Agent 自演化不只是学会技能”，先拆掉一个误解。
- **真实工作流视角**：例如 MCP server 那篇不是从协议定义讲起，而是从“哪些会一直留在我的配置里”讲起。

所以这篇的最佳方向不是“EvoMap 是什么”，而是：

> 我在真实工作里为什么需要 EvoMap；用了之后，Agent 的行为有什么肉眼可见的变化；普通用户可以从哪里开始。

这篇文章应该保留一点第一人称观察，但不要写成演讲稿。语气可以接近“我最近一直在遇到一个问题，于是做了一个小验证”。

## 推荐标题

**从反复解释到直接做事：我用 EvoMap 让 Agent 记住有效经验**

这个标题更接近 EvoMap 博客已有风格：

- “从反复解释到直接做事”给出变化路径。
- “我用 EvoMap”说明这是实际使用经验，不是抽象科普。
- “记住有效经验”比“自进化”“Gene / Capsule”更容易被普通用户理解。

## 备选标题

1. **让 Agent 记住有效做法：我用 EvoMap 少解释了多少上下文**
2. **Agent Memory 不够用时：我为什么开始用 EvoMap 沉淀经验**
3. **同一句需求，为什么接入 EvoMap 后 Agent 不再绕弯**
4. **EvoMap 实战：让 Coding Agent 不再每次从零理解你的项目**
5. **不只是记忆：EvoMap 让 Agent 复用已经验证过的经验**

## 文章目标

让普通用户读完后知道三件事：

1. EvoMap 解决的不是“让模型更聪明”，而是让 Agent 不再每次从零理解你。
2. 在真实工作里，EvoMap 的效果可以从“少反问、少纠结、直接给方案”看出来。
3. 普通用户可以用一个很小的场景开始，不需要一开始就理解完整技术协议。

## 读者预期

这篇文章不是给研究者或协议开发者看的，而是给这些人看的：

- 正在用 Cursor / Codex / Claude Code 的独立开发者。
- 同时维护多个项目，经常要给 AI 重复解释上下文的人。
- 有一堆服务器、数据库、文件服务、脚本和历史约定，但不想每次都重新说明的人。
- 想知道 EvoMap “到底怎么用、用了有什么变化”的普通用户。

## 核心定位

一句话定位：

> 这不是一篇讲协议细节的文章，而是一篇讲“普通用户如何让 Agent 少绕弯”的使用故事。

不要从 Evolver 原理开始。先从普通用户能感受到的变化开始：

```text
以前：我发一个需求，Agent 先问我一堆背景问题。
现在：我发同一句需求，Agent 先想起之前验证过的做法，然后直接给出方案。
```

机制只在后半段出现，而且用生活化表达：

```text
EvoMap 做的事情，可以简单理解成：
它帮 Agent 识别哪些经验值得留下，验证这些经验是否真的有用，再把它们变成下次可以调用的经验包。
```

## 建议结构

### 1. 我遇到的问题：Agent 不是不会做，而是总像第一次认识我

开头不要讲“AI 自进化”，先讲普通用户痛点。

建议写法：

> 我现在经常同时用 coding agent 做几个项目。问题不是 AI 不会写代码，而是它经常忘记我是谁、我的项目怎么分工、哪些规则之前已经定过。于是同一个需求，每次都要重新解释服务器、数据库、文件存储、发布路径和历史约定。

这一节只回答一个问题：为什么普通 Agent 会让人觉得“总在重新开始”。

这部分建议用 2 到 3 段，不要出现 Gene、Capsule、GEP。

### 2. 我的场景：几个项目共用同一批学习素材

这里保留你的实际使用场景，但不要展开太多技术细节。

压缩成三句话即可：

> 我是独立开发者，手上有一个日语学习网站、两个日语学习 App，还有一个把学习素材剪成短视频的流水线。
>
> 这些项目共用单词、语法、音频、插图和视频素材，但它们又分别面向网站、App 和视频发布。
>
> 所以我真正需要的不是“生成一个文件”，而是让 AI 理解：这些素材要被多个项目复用，并且国内和海外访问路径可能不同。

复杂信息放到脚注或附录，不要占正文篇幅：

- 有数据库服务器。
- 有 OSS / 文件桶。
- 有国内应用服务。
- 有海外加速入口。

正文里只保留“多项目共用素材”这条主线。

这一节不要超过全文 15%。它只负责让读者理解为什么这个需求不是一个简单的“上传文件”。

### 3. 同一句需求，普通 Agent 会怎么绕弯

放同一句需求：

```text
我要给 N5 单词卡生成一批音频和插图，上传到文件存储，并让网站、App、视频流水线都能复用。国内用户和海外用户访问路径不同。你帮我设计并落地最小实现。
```

然后展示普通 Agent 的典型反应：

- 你的服务器怎么分工？
- 文件存储怎么配置？
- 网站、App、视频分别读哪里？
- URL 是存在数据库里，还是每次生成？
- 海外访问是 CDN、代理，还是同步一份文件？

这里的判断要克制：这些反问不是错，而是普通 Agent 没有之前的经验可用。

建议在这一节结束时放一句判断：

> 真正浪费时间的不是 Agent 提问，而是它反复问那些以前已经解释过、甚至已经验证过的问题。

### 4. 接入 EvoMap 后，变化在哪里

这一节是文章核心，不讲协议，讲用户能看见的效果。

对比可以写成一张表：

| 同一句需求 | 普通 Agent | EvoMap Agent |
| --- | --- | --- |
| 起手式 | 先问背景 | 先回忆已验证经验 |
| 方案质量 | 泛泛建议，等用户补信息 | 直接给最小实现路径 |
| 用户成本 | 重复解释 | 只确认高风险动作 |
| 输出重点 | “你先告诉我系统怎么长” | “我按已知规则先这样落地” |

这节要落到一个具体方案上：

- 建一个共享素材清单。
- 文件上传后只记录对象 key 和校验信息。
- 不把固定完整 URL 写死。
- 按国内 / 海外访问区域动态生成地址。
- 网站、App、视频流水线都读同一份素材清单。

这就是普通用户最容易理解的效果：AI 不再从零问起，而是站在上一次经验上继续工作。

这一节建议配主图 `01-before-after-effect-zh.png` 或 `06-evolved-direct-path-zh.png`，让读者先看到效果。

### 5. EvoMap 在背后做的事：留下“被验证过的做法”

这一节只做轻量解释，不展开技术细节。

建议表达：

> EvoMap 背后的 Evolver 会从任务里识别信号，比如：用户反复纠正同一个问题、Agent 在同一个地方失败、某个方案被验证有效。
>
> 然后它会提炼出可复用的做法，再通过测试、执行记录或人工确认拿到证据。
>
> 最后，这些有证据的经验会被包装成下次可以召回的经验包。成功做法可以留下，错误示例也可以留下。

如果要放术语，只放一次：

```text
在 EvoMap 里，可复用做法可以理解成 Gene；经过验证的正向经验或错误示例可以理解成 Capsule。
普通用户不需要先记住这些词，只要知道它们最终会改变 Agent 下一次怎么回答。
```

这节可以放在文章中后段。不要把它写成“技术原理章”，而是写成“为什么这不是普通聊天记录”。

建议小标题可以用：

**EvoMap 留下的不是聊天记录，而是被验证过的做法**

### 6. 普通用户怎么开始用：先挑一个重复小场景

这一节要非常实用，避免写成安装手册。

建议写成 4 步：

1. 先选一个会重复出现的小场景。

   例如：素材上传、发布检查、数据库迁移、视频生成、日报整理。

2. 第一次把背景讲清楚。

   不需要讲全公司，只讲这个小场景里的项目、文件、服务和规则。

3. 让 Agent 在完成任务后记录“这次有效的做法”。

   重点不是记录所有聊天，而是记录被验证过的经验。

4. 下次发同类需求时，让 Agent 先 recall，再动手。

   用户只需要确认真正高风险的动作，比如写生产数据库、上传真实文件、发布到线上。

这一节可以配一句很直白的话：

> 不要一开始就试图让 EvoMap 记住你的一切。先让它记住一个重复出现的小问题。

这一节是“怎么用”的核心，建议比原理部分更长。

### 7. 我怎么验证它不是心理作用

这里引用开源 demo，但不要占太多篇幅。

写法：

> 我做了一个最小 demo，只比较同一句需求在两种状态下的回答：没有 EvoMap 时，Agent 先反问；有 EvoMap 经验资产时，Agent 直接给出共享素材方案。

保留命令即可：

```bash
git clone https://github.com/owenshen0907/evomap-agent-memory-demo.git
cd evomap-agent-memory-demo
python3 demo.py
python3 -m unittest discover
```

这一节不要写太像测试报告，只说明“可以复现行为差异”。

### 8. 结尾：EvoMap 对普通用户的意义

结尾收束到普通用户价值：

> EvoMap 对我来说，不是一个抽象的 AI 协议，而是让 Agent 从“临时帮手”变成“会积累经验的工作伙伴”。
>
> 它最先带来的变化也不是神奇自动化，而是少解释、少反问、少重复踩坑。
>
> 当一个 Agent 能记住哪些做法被验证过，哪些做法以前失败过，它就能在下一次任务里更快进入正题。

## 推荐开头草稿

> 我最近越来越明显地感觉到，用 coding agent 做长期项目时，最累的不是让它写代码，而是让它重新认识我。
>
> 我有几个日语学习相关项目：一个网站、两个 App，还有一条把学习素材剪成短视频的流水线。它们会共用单词、语法、音频和插图，但不同端的访问路径、素材组织方式和发布规则并不完全一样。
>
> 普通 Agent 第一次问我服务器怎么分工、文件存在哪里、视频流水线读什么数据，这是合理的。但当这些信息已经在过去的任务里反复出现，甚至有些做法已经被验证过，它还每次从头问一遍，我就知道问题不只是 context 不够，而是经验没有留下来。

## 推荐结尾草稿

> EvoMap 对普通用户最直接的价值，不是让 Agent 突然变成全自动系统，而是让它少一点失忆。
>
> 它能把一次任务里被验证过的做法留下来，让下次类似需求不再从“你先告诉我系统怎么长”开始，而是从“我记得这类问题之前怎么做有效”开始。
>
> 对我这种同时维护多个项目的人来说，这已经足够重要。因为长期工作里真正消耗人的，往往不是一次复杂任务，而是同样的上下文被反复解释，同样的坑被反复踩。
