## 图文版文章草稿

## Agent 不是不会做，而是总像第一次认识我

我最近越来越明显地感觉到，用 coding agent 做长期项目时，最累的不是让它写代码，而是让它重新认识我。

我有几个日语学习相关项目：一个网站、两个 App，还有一条把学习素材剪成短视频的流水线。它们会共用单词、语法、音频和插图，但不同端的访问路径、素材组织方式和发布规则并不完全一样。

普通 Agent 第一次问我服务器怎么分工、文件存在哪里、视频流水线读什么数据，这是合理的。但当这些信息已经在过去的任务里反复出现，甚至有些做法已经被验证过，它还每次从头问一遍，我就知道问题不只是 context 不够，而是经验没有留下来。

![同一句需求下，普通 Agent 和 EvoMap Agent 的起手式不同](images/mainline-gpt-image-2/zh/01-before-after-effect-zh.png)

我想解决的不是“让 AI 永远不问问题”。真正的问题是：那些已经解释过、验证过、甚至踩过坑的经验，能不能变成下次任务开始前就能用上的东西。

## 一个很小但真实的场景：多项目共用学习素材

我的真实环境可以展开很多细节：国内服务器、海外加速、数据库、文件桶、视频流水线、多个项目的发布规则。但如果一上来都讲出来，读者会被细节淹没。

所以这篇文章只保留一个最小场景：

> 我要给 N5 单词卡生成一批音频和插图，上传到文件存储，并让网站、App、视频流水线都能复用。国内用户和海外用户访问路径不同。你帮我设计并落地最小实现。

这句话背后有一个很普通但很真实的问题：我不是只想生成一批文件，而是希望这些文件变成多个项目都能复用的素材。

![多项目共用学习素材的最小场景](images/mainline-gpt-image-2/zh/03-project-topology-zh.png)

图里出现了不少基础设施，但正文不需要把它们全部讲清楚。普通用户只需要理解一件事：当一个人同时维护多个项目时，AI 不能只按“当前窗口里的单次任务”来理解需求。

## 同一句需求，普通 Agent 为什么会绕弯

如果把这句话直接发给一个没有历史经验的 coding agent，它大概率会先问一串问题：

- 服务器怎么分工？
- 文件存储怎么配置？
- 网站、App、视频分别读哪里？
- URL 是存在数据库里，还是每次生成？
- 海外访问是 CDN、代理，还是同步一份文件？

这些问题本身并不愚蠢。相反，一个谨慎的 Agent 就应该问清楚这些问题。

![普通 Agent 会先反问基础上下文](images/mainline-gpt-image-2/zh/05-normal-agent-question-path-zh.png)

真正浪费时间的是：这些问题以前已经问过，规则以前已经讨论过，有些做法甚至已经被验证过。Agent 如果每次都回到“你先告诉我系统怎么长”，用户就会被迫重复扮演项目说明书。

这也是我觉得很多所谓 Agent memory 还不够的地方。仅仅记住一段聊天记录，并不等于知道下次遇到类似问题应该怎么做。

## 接入 EvoMap 后，Agent 的起手式变了

接入 EvoMap 后，我希望看到的不是 Agent 变得更会背资料，而是它的第一步发生变化。

同一句需求，普通 Agent 的起手式是：

> 你先告诉我服务器、文件存储、数据库和视频流水线怎么配置。

EvoMap Agent 的起手式应该是：

> 我记得这类素材复用问题之前已经验证过一种做法：先建共享素材清单，文件上传后只记录对象 key 和校验信息，不把固定完整 URL 写死，再根据国内 / 海外访问路径动态生成地址。

![接入 EvoMap 后，Agent 先复用经验再给方案](images/mainline-gpt-image-2/zh/06-evolved-direct-path-zh.png)

这时它给出的方案会更接近可执行的最小实现：

- 建一个共享素材清单。
- 文件上传后只记录对象 key 和校验信息。
- 不把固定完整 URL 写进数据库。
- 按国内 / 海外访问区域动态生成访问地址。
- 网站、App、视频流水线都读同一份素材清单。

这不是一个很玄的能力，但它对长期项目很重要。它让 Agent 不再从“我完全不了解你”开始，而是从“我记得这类问题之前怎么做有效”开始。

## EvoMap 留下的不是聊天记录，而是被验证过的做法

EvoMap 背后的 Evolver 可以简单理解成一个经验筛选器。

它会从任务里识别信号：比如用户反复纠正同一个问题、Agent 在同一个地方失败、某个方案被验证有效。然后它会提炼出可复用的做法，再通过测试、执行记录或人工确认拿到证据。最后，这些有证据的经验会被包装成下次可以召回的经验包。

如果要用 EvoMap 里的术语来说，可复用做法可以理解成 Gene；经过验证的正向经验或错误示例可以理解成 Capsule。

但普通用户不需要先记住这些词。更重要的是理解结果：

> EvoMap 留下的不是“我说过什么”，而是“哪些做法被验证过，哪些做法下次应该避免”。

这也是它和普通聊天历史的区别。聊天历史很容易越堆越长，最后变成一团上下文。EvoMap 更关注的是：哪些经验值得留下，能不能被验证，下次什么时候应该召回。

## 普通用户怎么开始：先挑一个重复小场景

如果一个普通用户想试 EvoMap，我不建议一开始就试图让它理解整个公司、整个项目或所有服务器。

更好的方式是先挑一个重复出现的小场景。

可以是：

- 素材上传。
- 发布前检查。
- 数据库迁移。
- 视频生成。
- 每周日报。
- 某个固定类型的 bug 修复。

第一次，把这个小场景讲清楚。讲清楚涉及哪些项目、哪些文件、哪些服务、哪些规则。然后让 Agent 在完成任务后记录这次有效的做法。下一次再发同类需求时，让它先 recall，再动手。

这一步的关键不是记录所有聊天，而是记录被验证过的经验。

用户仍然应该确认高风险动作，比如写生产数据库、上传真实文件、发版到线上。但这些确认应该发生在真正要执行的时候，而不是每次都从基础背景开始问。

## 我怎么验证这不是心理作用

我做了一个最小 demo，只比较同一句需求在两种状态下的回答：没有 EvoMap 时，Agent 先反问；有 EvoMap 经验资产时，Agent 直接给出共享素材方案。

![开源 demo 用来复现同一句需求下的行为差异](images/mainline-gpt-image-2/zh/07-test-evidence-zh-v2.png)

你可以直接运行：

```bash
git clone https://github.com/owenshen0907/evomap-agent-memory-demo.git
cd evomap-agent-memory-demo
python3 demo.py
python3 -m unittest discover
```

这个 demo 不证明 EvoMap 能自动解决所有工程问题。它只证明一个更基础的差异：当 Agent 有了被验证过的经验资产，它的第一步会变。

对用户来说，这个第一步很关键。因为很多长期项目里的低效，不是来自一次任务特别难，而是来自同样的上下文被反复解释，同样的坑被反复踩。

## 少解释、少反问、少重复踩坑

EvoMap 对普通用户最直接的价值，不是让 Agent 突然变成全自动系统，而是让它少一点失忆。

它能把一次任务里被验证过的做法留下来，让下次类似需求不再从“你先告诉我系统怎么长”开始，而是从“我记得这类问题之前怎么做有效”开始。

对我这种同时维护多个项目的人来说，这已经足够重要。因为长期工作里真正消耗人的，往往不是一次复杂任务，而是同样的上下文被反复解释，同样的坑被反复踩。
